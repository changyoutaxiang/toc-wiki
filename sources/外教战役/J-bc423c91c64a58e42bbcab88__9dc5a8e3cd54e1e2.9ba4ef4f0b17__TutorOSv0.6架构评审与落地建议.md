# Tutor OS v0.6 架构评审与落地建议

评审日期：2026-09-07。范围：当前任务提供的 v0.6 HTML、AI 冷读稿，结合 CEO-Executive-Shared 只读资料。以下新增设计均为架构建议，不是已批准政策、工程现状或项目工期承诺。未访问附件所列其他本机来源，也未检查生产接口、代码或真实业务数据。

## 1. 结论与本轮核对

v0.6 可以作为总体架构讨论基线。下一步应围绕两条任务链补运行契约，主图可以保持稳定。文档完整度不代表生产成熟度。

## 2. 优先补齐的六项运行设计

### A. 从状态名称推进到状态转换与关闭规则

§5.2 已明确状态含义，但“交付、证据、恢复、服务处置”不能混进一个顺序枚举。建议分别维护以下维度，并由既有权威系统主写或提供引用：

| 维度 | 需要回答 | 不可替代的边界 |
|---|---|---|
| 原课交付结果 | 原来承诺的这一节课完整交付、部分交付还是未交付？ | 事后补课或补偿不能抹去原课受损事实 |
| 证据状态 | 有哪些证据、是否充分、是否存在争议或更正？ | 接口成功、无投诉和证据齐备分别判断 |
| 恢复案例 | 正在安排、已安排待发生、待核实、成功或失败？ | 找到替代老师不等于学生实际得到课 |
| 客户处理结果 | 继续恢复、接受其他处理、仍有争议或未能联系？ | 依据政策完成其他处理，可以形成结案结果，但不能计为教学兑现 |

对象应关联“一次排定的课”的唯一标识，避免将课程体系标识与具体课次混用。补课是另一课次时，应有原课—恢复案例—补课课次的关联。报表分别统计原课损失、恢复结果与最终客户处理，避免重复计算。

每条关键转换写清：当前状态、触发事件、事实前提、有效规则、允许执行主体、完成证据、超时去向、后续更正方式。至少明确：提出方案→预约成功、预约成功→实际交付、待验证→正式资格、人工接手→恢复自动运行。

### B. 把任务状态保存在持久系统里，并控制冲突动作

§7.1、§8.1 的“执行前再次核验”正确，但仍需防止两条任务同时检查通过后抢同一课位。

推荐责任分工：

- Agent 解释反馈、综合证据并提出行动意图。
- 持久任务状态机管理定时、接收确认、接手状态、重试和恢复。
- 排课等确定性系统在提交动作时校验资格、可用性和占用冲突，保证同一课位不会被重复承诺。
- 人在授权边界内确认敏感动作并处理例外；人工接手后，自动任务不能继续竞争执行。

最小可靠执行契约应包含：业务对象标识、关联事件、任务与动作标识、预期对象版本、证据与规则版本、授权依据、截止时间、幂等标识、动作回执和业务验证结果。这是字段语义建议，不是新平台 Schema。

必须处理的故障：

1. 同一告警重复到达：合并关联事件，不重复代课、发通知或建单。
2. 工具调用超时：先查询动作是否已生效；“结果未知”不能直接当失败重新执行。
3. 执行成功但回写失败：恢复回执与对账，不再重复执行业务动作。
4. 系统重启：从持久状态和到期任务继续运行，不靠聊天上下文重建。
5. 人工已接手：自动动作暂停；显式交还并重验当前状态后才继续。
6. 旧回复或旧告警迟到：保留发生时间和接收时间，不覆盖更新的资格、安排或交付结论。

优先要求蜂巢和原业务系统给出这些能力的验收证据；缺少时只补必要适配或受控人工步骤，不另建完整 Runtime。

### C. 将实时恢复与长期改善分成关联的两条任务链

即时链负责学生这一节课，慢速链负责老师或系统的改善。两者共享证据，完成条件不同。

- 即时恢复：异常出现→保护或恢复动作→真实安排→核实交付／客户处理。截止时间由距开课时间、课堂剩余时间和严重程度决定。
- 后续改善：归因→整改或训练→技术复测→新课堂观察→资格／匹配更新或规则变更候选。客户恢复不等待全部归因完成。

训练完成、设备测试通过和真实课堂改善应分别留证。7／14／30 天复发观察不能代替现场技术复测。

还需定义共同故障的处理：同一 Center 网络或平台故障触发大量老师告警时，先关联共因事件并限制重复行动；不能逐人自动判责、换师或反复触达。是否暂缓派课、切换替代路径及何时解除保护，由既有规则和授权决定。

### D. 把 TIDE 的三十天与有效试教暴露分开

§5.2 已明确试教许可和正式资格。还应把日历时间、适配试教机会、有效课堂证据分别计量。

“样本充分”应说明：实际完成的有效课次、覆盖的学生或任务类型、授课条件、证据质量，以及是否过度集中于单一简单样本。不能将缺少课位、数据丢失或匹配错误归为教师能力不足。

第三十天样本仍不足时，状态应维持“证据不足”，进入有截止时间与责任的补样、延长或人工判断路径。不得自动合格，也不能无限占用试用资源；正式处置仍按有效规则。

为防止 TIDE 与即时恢复争夺同一供给，首期需明确试用课位预算、支持能力上限和任务优先级；可由简单规则配置承载，无需先完成全局优化算法。试教支持条件缺失时，不能以“需要凑够样本”作为放行依据。

出营评估同时观察：范围内有效合格供给、出营后履约与质量、从入营到形成有效产能的时间及支持成本。后续课堂用新样本验证，并记录需求、难度、模式、时段等差异，避免把分配更容易的课堂误认为筛选或培养更有效。

### E. 明确跨 OS 的签收者与独立结果检查

文档已有 Tutor、Hive、Service、技术、Center 的边界，下一步按具体结果签收，避免多人“参与”却无人对结果负责。

| 结果 | 建议业务责任 | 权威事实／检查来源 |
|---|---|---|
| 原课及补课实际发生 | 课堂／排课系统提供事实 | 课堂事件、有效交付证据，不能仅凭 Agent 总结 |
| 客户恢复与处理结案 | Service 结果负责人 | 客户处理记录及适用关闭政策；Tutor 持续追踪关联结果 |
| 授课资格及限制范围 | Tutor 业务标准负责人 | 证据、适用标准、授权决定和独立复核 |
| 教学质量与学习证据解释 | Tutor 与课程／Learning 标准方协同 | 同一质量语义，避免 Tutor OS 独自重新定义“学会” |
| 设备／平台／场地改善 | 对应能力负责人 | 技术复测及后续真实课堂；分别证明条件恢复和客户改善 |

执行者不能是唯一裁判。硬条件由确定性检查执行，语义与证据质量由评测或抽样复核确认，高风险结果保留人工闸门。模型新增或规则更新后，旧结论须能追溯，但历史事实不被新解释覆盖。

学习更新分两路：新事实依规则更新对象状态；新的规则、Skill、Prompt 和模型选择先形成变更候选，再经过回放、签收和灰度。案例变多不应自动赋予 Agent 修改标准的权力。

### F. 用运行证据安排推进顺序

建议继续保留 2＋2 方向，但每个场景先跑最窄的完整链。坏课场景可选一种已有证据与处置入口的履约异常；TIDE 选一类授课资格和明确 cohort。具体范围由业务选择，不预设全球同时铺开。

| 阶段 | 要完成的工作 | 进入下一阶段所需证据 |
|---|---|---|
| 真实资产盘点 | 找到原事实源、对象、动作入口、授权方式和最小样例 | 能读到对象、解释数据、演示真实回执与失败状态；缺口有承接 |
| 历史回放与影子运行 | 同一批事件跑新规则，保留现有业务执行 | 正常、边界、失败与红线案例可解释；关键状态及动作一致性通过 |
| 受控试点 | 小范围执行低风险已授权动作，敏感动作人审 | 真实结果可核实，误伤与积压受控；两个场景共用协议实际成立 |
| 扩围与旧路径退役 | 按证据扩大课程／人群／模式，停止重复主写 | 业务改善持续，成本与人工承载可接受；恢复旧路径的方法明确 |

先约定误伤、未知动作积压、超时、支持队列和运行成本的停止条件；一旦触发，停止相关自动动作，保留观察并移交人工处理。不能简单关闭服务，让未完成课程失去承接。

历史回放用于验证机制正确性；影子运行主要验证识别与判断；真实试点才能验证执行效果。三者不能相互替代。复发率只纳入观察窗口足够且存在后续授课机会的样本；已暂停授课造成的“零复发”不能直接算作改善。

## 3. 首版必须演练的八类案例

以下为建议测试场景，不是已通过的测试结果。

| 案例 | 通过应呈现的行为 |
|---|---|
| 同课重复告警，TIDE 与坏课任务同时触发 | 关联同一事件，动作不重复，两个场景各有结果回写 |
| 两个恢复案例争抢同一替代课位 | 权威排课提交最多成功一个；另一个有明确安排路径 |
| 预约已成功但调用超时／回写失败 | 先查实际状态，再恢复回执，不产生第二次预约 |
| 资格暂停与匹配安排同时发生 | 按有效版本和提交时规则处理，禁止旧候选缓存直接放行 |
| 人工接手后旧任务醒来，或老师回复迟到 | 不抢回处理权，不覆盖更新决定，可查人工交还过程 |
| 客户接受其他处理但原课未交付 | 可按政策结案；原课受损和未教学兑现保持可见 |
| 第三十天试教样本不足 | 不自动通过或失败，有补样／延长／人工判断及截止条件 |
| Center／平台共同故障与系统重启 | 共因聚合、行动有节制，任务重启可恢复且不会逐人自动归责 |

## 4. 下一份交付应是什么

建议保持 v0.6 主框架，新增《首期运行契约 v0.1》，作为现有三份实施契约的具体内容，而非增加一套平行文档体系。最小交付包括：

1. 三类状态转换表：课程交付、恢复案例、授课资格；附主写方和关闭检查。
2. 一张动作与事件契约表：关联标识、版本、授权、幂等、未知结果查询、超时、人工接手。
3. 两条端到端样板：坏课恢复与 TIDE 各一条，配上述八类故障演练及验收证据。
4. 一份能力盘点与试点表：已验证可复用、需适配、尚缺能力；明确退出与迁移安排。

架构师负责把状态、契约和依赖接通；场景业务负责人签收规则与客户结果；底座及原系统负责人验证可靠执行；数据与 Eval 负责人确认口径、样本和评测。这里只定义责任类型，不指定个人或创设组织任命。

## 5. 依据与证据边界

- 当前任务附件：《Tutor OS 双视角框架｜AI 冷读版 v0.6》，重点 §5.1—5.5、§7、§8.1、§9.2、§10.4；配套 v0.6 HTML。
- Shared《Global Tutor OS》：对象、生命周期、跨 OS 接口、人工边界及阶段性验证限制。
- Shared《Loop Contract：蜂巢闭环契约》《Agent Hive 的 Loop Engineering》：跨时间状态、检查、停止、升级和业务／系统双重完成。
- Shared《Checker 与 Eval：蜂巢质量治理机制》：执行者不能是唯一裁判；确定性检查、Agent 检查、人工闸门；学习更新先形成候选并经回归与灰度。
- Shared《Harness Engineering》：可查询业务状态、可回放证据、测试、回滚、版本与自主等级相互约束。

这些 Shared 资料支持评审原则，不证明具体运行平台已提供本文列出的接口与能力。本文中的状态分维、可靠执行契约、两类任务链、试点门槛及演练案例是本次评审新增建议。
