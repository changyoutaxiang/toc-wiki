# 外教战役四化 How-to-Start v2.0

> 回答一个问题：**外教战役的四化建设，从哪里开始。**
> 三个先读懂的词：**卡** = 一个 md 文件 = 一张可计数、可复用的资产卡，口径/标准/判断写成卡才算资产；**L3** = 公司数据治理五层框架的"数据资产层"，Leon 负主责，职责五件事 = 定清单、拍口径、写说明、钉人头、踩刹车；**日心说** = 以 Agent 为中心的组织设计准则，流程、人、资源绕着智能体转。

---

## 1. 总命题：起点是一条生产线，不是一堆任务

四化起步常被拆成三件事：建卡的标准、按 Agent 为中心重排打法、数据治理破局。它们其实是同一台发动机的三个部件：

| 部件 | 是什么 | 在发动机里的角色 |
|---|---|---|
| 卡体系 | 资产的度量衡与封装格式 | 卡是 **Agent 的官方输入格式**——日心说下，卡的第一读者是 agent，不是人 |
| 日心说 | 设计准则：资产/流程/人绕着 agent 转 | 它回答"卡写给谁看、谁消费卡"——没有这条，卡只是更整齐的文档 |
| L3 数据治理 | Leon 亲投的定义权阵地 | L3 五件事**就是产卡五步**——L3 是战役的第一条卡生产线 |

**起点 = 这条最小生产线跑通一圈：产卡（Leon 在 L3 出样板）→ 用卡（agent 只引用卡回答口径问题）→ 计数（卡被复用的次数进周报）。** 跑通一圈后再复制给全员，而不是先全员铺开再求质量。

这条生产线同时给战役资产立了账本：团队资产卡数量 = 资产存量，产卡速率 = 系统进化速度，卡被他人/agent 调用次数 = 复用率。

## 2. 卡片体系与模板规范

### 2.0 设计原则（四条，所有模板由此推出）

1. **分类判据**：一类卡值得独立存在，当且仅当它的"本体区 schema"和"验收问题"与其他类不同。schema 相同的不许另立类型——防类型爆炸。
2. **头部高度统一**：所有类型共用同一份 frontmatter（同字段、同枚举），只有本体区按类型变化。任何系统/agent 只需会读一种头部，就能盘点全部卡。
3. **卡是字典，不是报表**：卡里放定义、口径、规则、理由；不放随时间变化的数值。数值只允许以"带日期戳的快照"出现在指定区。数值变了不改卡，口径变了才改卡。
4. **第一读者是 agent**：每个字段都要经得起一个问题——"agent 拿这个字段能回答什么业务提问？"回答不了的字段删掉。

> **L 层级口径锚定（[[FT-DEC-005_圣经与指标卡schema对齐|FT-DEC-005]]，2026-06-22 Leon 裁定选 A）**：卡库一切「L 层级」一律以**公司五层**为准——L1 同步 / L2 数仓 / L3 数据资产 / L4 服务 / L5 使用。引用公司「数据圣经」dbt 式三层时加映射：圣经 **L3 官方数据集 = 公司 L3 数据资产**；圣经 **L2 标准明细 ≈ 公司 L2 数仓**；圣经 **L1 源表 ≠ 公司 L1 同步层**（圣经 L1 = 源系统更底层，公司 L1 = ODS 同步，引用必点名此错位）；圣经无 L4/L5，其「BI 数据源 / 统一口径入口」≈ 公司 L4 服务 + L5 使用。

### 2.1 类型总览（5 类）

| 类型 | type 值 | 回答什么问题 | 典型产出场景 | 验收问题（agent 预检用） | 晋升分支 |
|---|---|---|---|---|---|
| **数据集卡** | `card/数据集` | 这堆数据是什么、从哪来、能信吗 | L3 定清单：Teacher Master、Lesson/Booking、Quality Event… | "X 字段什么含义？数据从哪来、多久更新？哪些报表在用它？" | 可执行 |
| **指标卡** | `card/指标` | 这个数怎么算、唯一口径是什么 | L3 拍口径：B+/A 占比、通过率、booking share… | "分母含不含 Y？和 Z 报表的数为什么不一样？口径哪版？" | 可执行 |
| **标准卡** | `card/标准` | 过线不过线、谁说了算 | 划线裁决：设备 3500 线、口音子标准… | "对象 W 过不过？为什么？例外谁批？" | 可执行 |
| **决策卡** | `card/决策` | 当时为什么这么定 | 每次裁决会随手产 1 张 | "当时备选项是什么？为什么否了？什么情况下该重议？" | 洞察 |
| **流程卡** | `card/流程` | 这件事怎么跑 | SOP 沉淀；skill 是它的代码形态 | "新人/agent 照卡能不能独立跑完一遍？" | 可执行 |

三组关系一句话记：**指标卡量世界，标准卡划线，决策卡留 why；数据集卡是前两者的地基，流程卡把前三者串成动作。**

"数据卡"= 数据集卡 + 指标卡两个子型。不合并的原因：一个描述资产（对象/字段/来源），一个定义计算（分子/分母/算法），schema 与验收问题完全不同；合并就会出现一张卡里"字段表"和"分子分母"互相空着的烂卡。指标卡收编战役既有的"指标定义卡"模板（旧模板进退役总账），不另立格式。

暂不立类（防爆炸）：人物卡、案例/反例卡——真实需求出现满 3 次再立，立时走 §2.0-1 判据。

晋升分支注：**可执行卡**（数据集/指标/标准/流程）的晋升闸门 = 第二个人/agent/系统不找作者就能用出有效结果；**洞察卡**（决策）的闸门 = 改变了非作者的一个决策，或被实际引用。

### 2.2 统一头部（所有类型共用，逐字段强制）

```yaml
---
card: 数据集            # 枚举：数据集 | 指标 | 标准 | 决策 | 流程
id: FT-DS-001          # 全局唯一编号，台账发号，见 §2.5
title: Teacher Master 老师主数据集
domain: 外教战役
owner: 王东             # 必须是具体人名，写"团队"= lint 不过
status: 候选            # 枚举：候选 | 复核 | 资产 | 退役（按卡晋升协议四态）
created: 2026-06-10
effective: 2026-06-11   # 生效日；标准卡/指标卡必填，其余可空
sources:                # 出处：会议纪要 / 决策 / 数据表路径
  - projects/TOC/会议/正文/xxx.md
supersedes: []          # 本卡取代的旧口径/旧卡/旧 Excel（同步进退役总账）
used_by: []             # 消费方：引用本卡的卡 ID / 报表 / 系统 / agent
---
```

| 字段 | 必填 | 规则 |
|---|---|---|
| card / id / title / domain / owner / status / created | 全类型必填 | 枚举值不得自造 |
| effective | 标准、指标必填 | 没有生效日的标准不是标准 |
| sources | 必填（≥1） | 出处不可考的卡不收 |
| supersedes | 取代了旧东西时必填 | 与旧路径退役总账双向同步 |
| used_by | 入库后由台账/agent 维护 | 复用计数的数据源 |

### 2.4 卡间链接结构（体系而非堆）

```
数据集卡（地基：资产本身）
   ↑ 基于
指标卡（量世界）
   ↑ 尺子
标准卡（划线）
   ↑ 产生/修改
决策卡（留 why）          流程卡（把以上串成动作，引用标准/指标）
```

上图是**计算依赖**（指标算自数据集，数据集是地基）。**生产时序与之相反（2026-06-10 外部反馈修正）**：

```
业务流程 → 业务问题 → 先定指标 → 倒推数据集 → 数据服务（L4 报表）→ 业务使用（L5）→ 回到业务流程（闭环）
```

需求拉动，不先囤数据集——自底向上铺数据集是数仓项目的经典死法（建一堆没人查的表）。本战役排产已按此序：通过率指标卡 06-13 先行，Teacher Master 数据集卡 06-30 收口。

两条硬规则：

1. **指标卡必须链到数据集卡（计算依赖完整性）**——没有地基的指标是野口径换马甲。但**不要求数据集先建成**：由指标倒推，先立"骨架数据集卡"（只有对象/粒度/字段需求清单，可信度标低）占位，随治理充实。
2. **每次裁决会出卡成对**：拍死 N 个口径/标准 → N 张指标/标准卡 + 1 张决策卡（why）。口径进可执行分支，理由进洞察分支，互相引用。

### 2.5 命名与编号

- **ID**：`FT-<类型码>-<三位序号>`。类型码：DS（数据集）/ IND（指标）/ STD（标准）/ DEC（决策）/ SOP（流程）。序号由台账 `系统资产卡/_index.md` 顺序发号，不复用、不跳号。
- **文件名**：`<ID>_<短标题>.md`，如 `FT-IND-001_BA占比-招聘端.md`。
- **title**：含业务关键词、能被搜到；禁用内部黑话和缩写孤儿。

### 2.6 卡 lint（入库前 10 条，agent 可自动检查）

1. frontmatter 字段齐全，枚举值合法
2. owner 是具体人名，不是团队/部门
3. **一卡一事**：一个指标 / 一条标准 / 一个决策；正文里写出第二个"和"就拆卡
4. 指标卡的"基于数据集卡"非空
5. 标准卡 / 指标卡有 effective 生效日
6. 数值只出现在快照区且带日期戳
7. sources ≥ 1 且路径真实存在
8. supersedes 与旧路径退役总账双向同步
9. 不含个人隐私 / 薪酬个案 / 未公开人事信息
10. **agent 预检通过**：非作者出 3 个真实业务问题，agent 仅凭本卡答对，记录附台账（预检 ≠ 晋升——晋升仍按卡晋升协议走真实复用）

### 2.7 轻重分级与晋升

以上五类都是**轻卡**（10 分钟写完的候选卡格式）。**重卡 = 系统资产卡（10 格模板，已有）**：标准要进系统锁定（PRS/广告/脚本/gating）、管存量治理与旧路径退役时，由轻卡按 10 格补全升级。轻卡管"定义清楚"，重卡管"运行起来"，台账保留双向链接。

流转沿用卡晋升协议四态：**候选卡 → 复核卡（一次非作者复用）→ 团队资产卡（过闸门，计入资产存量）→ 退役卡（降格存档不删）**。**复用主体包括人、agent 和系统**——卡进 PRS/广告/脚本等系统锁定，即记一次系统复用（设备卡 06-11 上线即凭此晋升，不走特权通道）。战役域晋升判决权归 Leon。复用计数从手动起步（周收束统计，进周会表扬墙），**前 90 天只表扬不进 KPI**——组织史上标准化的头号死因是"KPI 按月度/季度锁死 vs 四化产出周期 6-18 个月 → 表演四化"，不重蹈。

### 2.8 卡库载体：团队侧是正本，Leon 侧是治理台账

卡库若只落在 Leon 个人 vault，团队成员读不到也写不进，"人人构建原子"就落空。故分双层：

- **团队侧（卡库正本，全员可读写）**：落在团队可达的公司设施——COO 倾向**钉钉知识库**（全员已有账号，agent 经 dws 通道具备全套读写命令）。**冒烟测试判据**（开闸前提）：一张完整卡——含 frontmatter 与卡间链接——写入后，agent 经 dws 读回并解析出全部字段；钉钉不是 md 原生宿主，frontmatter/wikilink 能否存活正是要测的点，测不过则降级到共享 repo 方案。
- **Leon 侧（治理台账 + 镜像）**：`系统资产卡/_index.md` 升级为全战役卡台账（轻重都登记、发号、记预检与复用）；重卡正本暂留 Leon 侧，团队侧放只读副本。

配套一页纸（先让人懂，再让人写）：《什么是卡：为什么写、10 分钟怎么写》+ 1 张真样例（设备达标卡）。**写作红线：零内部黑话**，只讲三句人话——①口径写成卡，吵架就结束了 ②卡写好的标志是 AI 能替你回答 ③你的卡被别人用一次，算你一次贡献。

## 3. L3 起步：Leon 亲投的第一条生产线

L3 五件事与产卡的映射——这就是为什么 L3 是天然起点：

| L3 五件事 | 产卡动作 |
|---|---|
| 定清单 | 7 个 P0 数据集 + 20-30 指标 list = 卡库的排产清单 |
| 拍口径 | 每拍死一个口径 = 一张指标卡的本体 |
| 写说明 | 卡的正文——**第一读者是 agent**，新员工是第二读者 |
| 钉人头 | 卡的 owner 字段（不许写团队） |
| 踩刹车 | 周会"这数从哪来的？口径哪版？"——标准答案必须是卡指针 |
