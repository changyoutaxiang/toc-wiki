## 二、现有功能优化（基于普遍反馈）

### 1. 新学员用户画像
- **痛点**：LP / SS 不知道怎么帮新学员固定老师，也不知道用户喜欢什么样的老师。
- **方案**：先给新学员搭建用户画像，基于上课记录 + 评价数据分析偏好，默认选中并推荐对应类型老师。
- **范围**：一期先只针对新学员（画像分析有**成本**，且新学员尚无评价数据）。
- **细节修正**：分享/截图文案要精简，避免字段过多导致信息外泄（"四个容易二命"）。

### 2. 一键分享外教详情页
- **痛点**：找到合适老师后，原来要手动截图资料 + 下载自我介绍视频 / 精彩瞬间，再发家长，繁琐。
- **方案**：新版增加一键分享入口，直接复制 H5 外教详情页给家长，内容更全。分享卡片显示"给您分享一个优秀的老师"（poly 字样后续换成自有门户）。
- **进度**：预计 **6 月中**可用。

## 三、AI 推荐算法（火山引擎）—— 核心战略讨论

### 现状与方案
- 当前线上推荐是自研简单版；**火山引擎**有完整的用户画像闭环推荐系统（基于抖音推荐引擎），含正/负向数据，只要把埋点 + 行为数据喂进去即可。
- 火山后台规则目前**基本是空的**（提权 / 降权 / 召回排序 / 重排等）；5 月中跟蔡老板开会后只加了"缺席、收藏"等极少指标。
- **行为数据映射**：曝光 → 筛选 → 约课 → 解绑 → 好评 → 收藏，灌进火山做千人千面。
- **计划**：6 月中梳理底层数据并接入火山 → 6 月底调试算法。未来对接两个接口：**搜索 + 推荐**。

### 王东的核心判断（餐厅比喻）
- 产品分两步：① 先在**性能/功能**上让大家"从解放前到解放后"（先吃饱、瞬间好用）；② 再上**算法准不准**（菜好不好吃 = 引擎）。
- **引擎是战役的"发动机"，自己造不了**（靠火山），靠吃反馈持续进化。第一轮一定不准，要靠投喂迭代变聪明。
- 菜好不好吃决定"饭店第二天还来不来"——是决定成败的硬核项。

### ⚠️ 关键空缺：引擎进化谁来 own（未决）
- 火山的人不懂业务，业务的人不懂算法 → **需要 someone 既懂业务又能 own 算法引擎的持续迭代**，是当前最大问号。
- 海璇暂时表态愿意为引擎进化负责；王东也愿意投时间进来。
- **风险点**："海璇变黄/老司机病"——只有海璇一人吃透，其他人看着懵，知识不可迁移。
- **行动方向（王东）**：把海璇的经验快速 output 成 skill / 流程，打通可复用。

### 多供应商 A/B 与配置策略
- **双供应商竞赛**：自研详情 + 火山，B 端还引入阿里（李勇）；让火山和阿里"拼"，谁跑赢用谁（"拼好了不给钱"）。当前先用火山。
- **区域策略**：火山支持新建多个策略，可按区域分别调（中东单独策略）。
- **实时性约束**：火山是实时的，但要看**我方数据传输是否实时**——若数据是 T-1，则引擎调不动。
- **验证口径**：2–3 周后用**好评 / 收藏**等数据 measure 推荐准确率。

### 驻场 vs 自建（讨论结论）
- 可让第三方（火山 / 蔡老板算法团队）派**技术支持驻场**调（不额外收费）。
- 但**业务策略驻场的人做不了**（不了解业务，只能告诉你"不准"，不知道怎么调）。
- **结论**：团队自己先配一版 → 集体跟火山学一遍、都有体感 → 再看是否找一个人专职在这调。掌勺的厨子不能离锅（需持续盯数据、调策略）。
