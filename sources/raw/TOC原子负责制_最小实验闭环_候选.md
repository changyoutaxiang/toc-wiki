# TOC 原子负责制的最小实验闭环（候选方法）

## 一句话

外教侧任何改革、驱动或新规则，先拆成一个**尽可能小、可测试、带明确反馈**的最小实验；由一个明确 owner 对结果负责，并以证据而非层级争论决定扩大、迭代或停止。

## 它要改变什么

这不是把产研的 MVP 习惯搬进业务，而是把 TOC 的决策成本降下来：把“多人讨论一个大方案”改造成“一个原子单元跑一个受边界保护的实验”。这样不必让每个局部决定都上推到传统金字塔，组织速度来自反馈授权，而不是更多会议或更快审批。

AI native 提供拆解、记录、观测、比较与复用的低成本能力；制度设计负责统一边界、反馈口径和复盘节奏。人仍对客户价值、关系、复杂取舍和最终责任负责。

## 原子单元的最低合同

每个实验只需说清六件事，不新增长文或额外审批：

1. **要验证什么**：一个与客户、老师或业务结果有关的假设；
2. **最小范围**：试点对象、时段／样本，以及明确“不做什么”；
3. **唯一 owner**：谁对实验的运行和结果负责；
4. **变量与对照**：改变什么、与什么比较；
5. **反馈**：看什么信号、多久看一次，领先信号与结果信号分别是什么；
6. **决策门槛**：到期后按什么条件 Scale／Iterate／Stop。

没有最小范围、没有反馈、没有扩大／迭代／停止门槛的，还不是一项改革，只是一个想法。

## 中央与原子的边界

- **中央／TOC 一线负责人**：守北极星、客户与老师信任红线、关键口径、跨原子资源冲突；
- **原子单元**：在边界内选择做法，快速把假设变成可观察的结果；
- **反馈回路**：不把局部活动量或单一内部采纳当胜利。CC 使用、交付速度等可以是领先信号；客户选择、履约、学习体验、留存／投诉等才是结果校验。

因此，原子负责制不是放任式分权，也不是用“小试试看”替代经营判断；它是受共同目标和红线约束的、可逆的分布式学习机制。

## 当前落点与状态

战役二的 7/22 作战设计已采用同一骨架：MVP 实验卡要求对照、变量、样本、周期与停止／扩量条件，并以 Scale／Iterate／Stop 作为决策出口。该方法把这项既有做法上升为 TOC 的共同决策语言，而不另造一套流程。

本文件是 **候选方法**，供 Leon、COO 与 agent 召回和检验；它不是已向团队生效的新规则，也不构成 KPI、人员评价或对外承诺。若要正式生效，应另走相应的业务裁决与发布 gate。

## 2026-08-14 增量：共同现场是方法的一部分

当天的全量老师触达与鹰眼/坏课治理小队，补出了一条更具体的运行假设：原子单元不能只把技术当作接收产品需求的下游。技术、运营与产品应围绕同一客户任务共同到现场，先理解客户状态、边界和可验证结果，再决定系统解法。

AC 关闭时老师端强提醒弹窗的现场 demo 是一个正向样本：当技术理解“需要与老师建立有效触达”这一任务后，提出了直接、低摩擦的方案。它只证明了现场协作可能改善解法质量；尚未证明上线覆盖、客户结果或原子负责制本身已经有效。

因此，本方法的最低合同补充为：

7. **共同上下文**：关键技术、运营与产品角色必须直接理解客户任务和现场约束，而不只消费转译后的功能清单。

验证标准不变：只有客户结果、护栏、可复盘证据和非作者可接续资产同时出现，才可把现场协作从工作假设升级为可复制的方法。
