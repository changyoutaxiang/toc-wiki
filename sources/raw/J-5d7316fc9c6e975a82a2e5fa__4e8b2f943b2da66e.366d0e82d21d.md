# 架构师零基新框架｜会话转贴

我会从“教学任务、老师能力和交付条件如何共同产生学习价值”重新设计 Tutor OS，再推导核心循环、人与系统的分工，以及第一步该验证什么。既有方案只作为经验参考，不预设必须保留哪些模块。

这个设计的关键，是让系统同时具备两种能力：为眼前的教学任务组织合适的老师和支持，也能通过训练、工具与教学方法，形成未来需要的能力。三条循环必须共享同一套交付证据，否则招聘、教学支持和质量治理仍会各自运转。

**如果从零设计，我会把 Tutor OS 定义为：持续形成学生需要的教学能力，把它可靠地组织到每一次真人教学任务中，并让整个教师网络从交付中变得更强。**

这里有三个必须同时成立的结果：学生获得有效的教学支持；老师越来越有能力、也愿意持续参与；公司能够以可持续的成本扩大交付。

Shared《Global Tutor OS》已经明确了教师教学支持、供给经营、跨 OS 协同和人工责任边界。下面是基于这些边界提出的**新架构建议**，不代表已有系统已经实现。

**一、从第一性原理出发：先定义需要产生什么变化**

我会从学生的一项具体需要开始：

> 这个学生，在这个阶段，需要真人帮助他完成什么变化？

例如：学生已经会回答简单问题，但还不能围绕一个主题主动展开交流。下一阶段需要的真人教学能力，是诊断表达障碍、组织真实对话、适时提供帮助，并逐步撤去提示。

由此才能推出：

- 老师需要具备什么能力；
- 需要什么材料、工具和学情信息；
- 什么授课环境和时间安排才可行；
- 是否需要保持同一位老师的连续关系；
- 用什么证据判断这次支持有效。

**“一节课”是交付单元，“教学任务”是价值单元。** 一个教学任务可能需要连续几节课完成；一次课堂也可能只完成其中一步。系统必须同时看见这两个层次。

Learning OS 负责定义学习需要、学习路径和进步标准；Tutor OS 负责回答：**怎样组织真人教学，才能可靠地满足这个需要？** 如果现有能力无法满足，就把限制和可行替代方案反馈回去。

**二、系统经营的核心，是“在明确条件下可以兑现的教学能力”**

这里需要再作一个关键区分：

**老师自身已经证明的能力，与老师在某套支持条件下能够完成的任务，要分别记录。**

一位老师借助成熟教案、备课支持和课堂工具，可以胜任某类任务；撤去这些支持后，未必仍然胜任。系统不能把工具和环境带来的效果，全部记成老师个人能力；也不能把环境失效，直接记成老师能力下降。

因此，我会让以下六类业务对象构成核心：

| 核心对象 | 系统必须知道什么 |
|---|---|
| **教学任务** | 学生需要什么变化，时限、连续性和验收证据是什么 |
| **能力证据** | 老师在什么任务、什么条件下证明过什么能力，还有哪些未知 |
| **教学支持方案** | 需要哪些教案、工具、备课帮助、设备与专业支持 |
| **教学安排与承诺** | 谁在什么时候，携带什么支持，承担哪项任务 |
| **交付与效果证据** | 实际发生了什么，任务完成到哪一步，哪些判断仍不确定 |
| **改进方案与验证** | 准备改变什么，为什么，以及怎样证明改变有效 |

老师档案，是围绕老师呈现这些信息的视图。能力判断必须能追溯到证据、适用条件和版本。

“合格”也因此成为一个有范围的结论：

> 在这些条件下，可以独立承担这类任务；另一些任务需要支持、进一步验证，或暂时不宜承担。

资质底线、教学能力、当前设备状态、可用时间和老师意愿分别表达，避免压缩成一个总分。

**三、让三个循环驱动整个系统**

```text
学习需要与未来需求
        ↓
形成所需能力 ─────→ 组织教学、兑现任务
    ↑                     ↓
    └──── 验证与传播改进 ← 交付与效果证据
                 │
                 └────→ 改善下一次教学安排
```

**第一个循环：形成所需能力。**

系统持续识别：未来哪些任务，在什么时间和地区，会缺少可用的教学能力。

面对缺口，可以选择训练现有老师、改善教学支持、解决环境限制、招聘新老师，或者向上游反馈当前不可承诺的需求。

这使招聘和训练都有明确的需求牵引。TIDE 可以成为其中一种能力形成路径：筛选、训练、受支持的试教、真实任务验证，再决定可承担范围。

这个循环的产出是：**新增了多少有需求、可验证、可实际调度的教学能力。**

**第二个循环：组织教学、兑现任务。**

系统为一项任务组织完整安排：

> 合适的老师＋必要的教学支持＋可行的授课条件＋连续性安排。

随后帮助老师备课、开展教学、获得支援、提交证据，并对未完成事项持续负责。

异常恢复是这个循环的必要分支。正常课堂同样要有证据回流：老师用了什么方法、学生在哪一步遇到困难、下一次需要怎样调整。

关闭时分别验证：

- **交付是否兑现：**约定的教学是否实际完成；
- **教学是否有效：**产生了什么与目标有关的证据。

后一项由 Learning OS 的标准和相应专业责任方验证。需要延迟复测的结果可以后续回流，不能为了结单提前宣称学生已经掌握。

**第三个循环：验证和传播改进。**

系统从真实交付中发现值得检验的改进：某种备课支持、训练方法、匹配条件或设备调整，可能让一类任务完成得更好。

然后经过：

> 提出假设 → 小范围验证 → 检查适用条件和代价 → 签收 → 扩大使用 → 持续复检。

这个循环尤其要防止把相关性当成因果。学生进步较快，可能与老师、学生起点、课程、连续性或家庭条件有关；单次结果只能贡献证据。

**“系统会学习”应当具体表现为：经过验证的做法进入下一次训练、支持和安排，失效的做法能够被修正和退役。**

**四、老师端，是整个系统形成能力的主要现场**

我会围绕老师每天的四项任务设计产品：

- **课前：**帮助我理解这个学生、这次目标和最值得准备的地方。
- **课中：**让我及时获得所需材料和支援，尽量减少对教学的干扰。
- **课后：**帮助我识别学生发生的变化，以及自己下一次最值得改进的一点。
- **长期：**让我知道能够承担哪些任务、怎样拓展能力，以及成长会带来什么机会。

老师还必须能够主动表达：自己希望承担什么任务、哪些条件发生了变化、哪里需要帮助、哪些系统判断有误。

因此，**老师既是教学执行者，也是专业判断和系统改进的重要来源。** 纠错、申诉、经验贡献和主动求助，都要进入正式流程。

运营端则围绕三个问题组织：哪里有能力缺口，哪些交付需要介入，哪些改进值得投入。两端共享事实，各自服务不同任务。

**五、架构上，明确谁定义、谁判断、谁执行、谁负责**

| 责任方 | 核心职责 |
|---|---|
| **Learning OS** | 定义学习任务、学习路径和进步证据，判断何时需要真人 |
| **Tutor OS** | 定义任务对应的能力要求、教学支持、供给安排、履约和能力改进规则 |
| **Service OS** | 承接客户沟通、信任恢复及跨域服务事项 |
| **Growth OS** | 在可兑现供给范围内形成商业承诺 |
| **Agent Hive** | 提供任务执行、Agent 运行、权限、Trace、Eval 等共同机制 |
| **确定性业务系统** | 可靠维护排课、课堂、合同、权益和课酬等正式状态 |
| **人类责任方** | 签收标准、处理专业争议和重大权益变化，承担最终责任 |

Tutor OS 内部，我会先建立**明确的任务状态与规则，再配置承担窄任务的 Agent**。Agent 可以整理证据、提出匹配与支持建议、解释反馈、执行授权动作；正式状态变化通过受控接口完成。

每项跨域任务都要有一个明确的结果责任方。各系统交接需要有接收和结果回执，才能保证任务持续有人负责。

这些是目标责任边界。蜂巢实际提供了哪些服务，还需要逐项核验；架构图上的能力不能直接算作实施依赖已经满足。

跨区域则统一对象、证据结构和协同方式，把语言、课程标准、资质要求、授课条件及政策放入可版本化配置。新区域可以复用运行机制，但教学效果需要在当地条件下验证。

**六、从零落地，我会先跑通一个完整的教学任务类型**

我不会把“全量监控、全量触达完成”设成业务验证的前置条件。第一步只建设试点所需的感知和行动能力，同时记录覆盖盲区。

选择一类边界清楚、需求真实、结果可观察的教学任务，完成一次贯穿三个循环的试点：

1. 教学专业负责人定义任务、能力要求和验收证据。
2. 用历史课堂和模拟任务校准判断，明确未知与误判。
3. 为符合基本准入要求的老师提供具体教学支持，在受控范围内开展真实交付。
4. 验证支持是否改善教学表现、学生结果和老师负担。
5. 把通过验证的方法用于另一组老师或任务样本，检验能否复用。

在这条路径中，新师训练、备课支持、课堂感知、异常恢复和能力更新会自然连接起来。

试点还要回答一个资源决策：**面对同一个能力缺口，培训、改善工具环境和新增招聘，哪一种更有效、更可持续？** 这决定下一阶段应当建设什么。

**七、用业务结果和能力积累共同验收**

我会要求同时看五组结果：

| 验收方向 | 要证明的结果 |
|---|---|
| **学生价值** | 任务稳定兑现，并有符合学习标准的效果证据 |
| **能力形成** | 更多老师在明确条件下，能够可靠承担实际需要的任务 |
| **老师体验** | 支持确实有用，准备与操作负担可承受，老师愿意继续参与 |
| **经营可持续性** | 单位有效交付的总成本可接受，运营介入量不随规模同比增长 |
| **系统积累** | 有效方法能被其他老师复用，关键决策可回放，重复人工路径逐步退出 |

具体门槛应在试点前根据基线共同签收。不能通过减少困难学生服务、过度集中课量，或把负担转给老师来制造指标改善。

若效果证据不足，就继续验证；若出现明显教学风险、错误限制授课范围或支持负担过高，就暂停扩展并修正。试点业务负责人对结果负责，教学专业负责人签收效果，架构与数据负责人保证证据可信、运行可追溯。

第一轮我会实际交付四件东西：**一份教学任务契约、一套带适用条件的能力证据、一条老师真正用得上的教学支持流程，以及一份证明它有效或无效的验证报告。** 这四件形成之后，再决定哪些能力值得扩成 Tutor OS 的公共核心。
