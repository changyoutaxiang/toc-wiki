# Tutor OS 双视角框架｜AI 冷读版 v0.6

## 0. 冷启动摘要

本文件描述 51Talk 外教战略讨论中的两个视角。第一张图组织业务，第二张图组织系统建设。二者指向同一个教师供给与教学交付体系，共享客户目标、事实和已确认约束，允许采用不同粒度、推进节奏与验证方式。

**共同目的：高质量供给，持续产生客户价值。** 客户价值指学生持续获得适配、可靠、有质量的教学，以及学习成长、体验与信任；不能仅用招聘量、训练营通过率、通知量或 Agent 运行量替代。

最先记住以下十条：

1. **业务视角：从现在走向未来，追求更多确定性。** 回答如何形成高质量供给、持续经营教师，并把供给转化为学生的好教学。
2. **系统建设视角：从未来锚定现在，追求更多正确性。** 从目标运行机制倒推共同对象、规则、执行、反馈与首期建设范围。
3. **保留两个视角、两张图，不强行融合。** 这不是相同内容换两套排版，也不是两个独立系统。
4. **业务主图已经选定。** 采用四个业务域：供给制造、筛选、日常运营、客户价值输出；包括五项日常功能、三项全局基础能力，以及 Hive 支撑的跨域运行关系。
5. 原来标为“OS 建设视角”的四域图，已由 Leon 重新确认为业务视角标本。业务图表达基本成熟，不表示业务建设已经完成。
6. **系统首期采用 2＋2：** 鹰眼全监控、老师全触达两项能力；坏课治理、TIDE 筛出合格老师两个业务场景；两场景共用系统主干。
7. **2＋2 是首期推进结构，不是 Tutor OS 的全部边界。** Center、匹配、成长、供需等业务工作不会因未列入两个首批场景而从战略中消失。
8. 系统图使用职责名称：**事实与证据 → 业务对象与状态 → 判断与规则 → 行动与结果**；权限、审计和评测贯穿全程。课程兑现与授课资格必须有可查询状态，不能埋在老师档案长文中。
9. 全局供需统一算法必须由 Tutor OS 承载。首期 2＋2 不自动完成完整算法，但试用课位、替代老师的最小供给查询与资格检查必须有承接方案；运行上可由 Hive 调度。
10. 当前交付是双图讨论稿及本冷读文档。系统分层、对象契约、运行链和验收方法仍包含设计建议，不能据图声明系统已上线、政策已生效或客户效果已验证。

## 2. 两视角的正式定义

| 维度 | BUSINESS：业务战略视角 | SYSTEM：Tutor OS 建设视角 |
|---|---|---|
| 方向 | 从现在走向未来 | 从未来锚定现在 |
| 核心追求 | 增加业务选择与推进的确定性 | 提高运行机制与建设路径的正确性 |
| 起点 | 现有老师、学员、供给模式、运营能力和业务问题 | 应当持续兑现的好课，以及支撑兑现的目标机制 |
| 核心问题 | 做什么、为什么做、如何形成供给与客户价值、现实取舍是什么 | 需要什么共同能力，怎样组织事实与动作，结果怎样改变下一次 |
| 主要分析单元 | 业务域、教师阶段、经营机制、客户结果 | 场景、对象、分层、状态转换、能力契约、执行与验证 |
| 当前图形 | 四域业务全景＋五项日常功能＋三项基础能力 | 两个首批场景＋四段共用主干与贯穿治理＋两项共用能力 |
| 验证重点 | 高质量供给是否形成、学生是否持续获得好教学 | 业务链能否实际完成、能力能否复用、失败能否解释和纠正 |
| 本轮成熟度 | 主图标本已接受，具体经营主张仍逐项打磨 | 首期 2＋2 有后续确认输入，具体技术表达与契约仍在探索 |

“确定性”与“正确性”是两图的侧重点，不是说业务可以忽视正确性，或系统无需验证现实可行性。

### 2.1 集合与关系

```text
同一目标域：教师供给、经营与教学交付
├─ BUSINESS 投影：把完整业务体系按价值形成过程组织
└─ SYSTEM 投影：把目标运行机制按能力、对象与责任组织

共享事实 + 共享目标 + 已确认约束
          ↓
具体业务场景 ↔ 系统能力及契约 ↔ 真实结果与复用证据
```

两视角的联系是多对多关系，不是 `BUSINESS.module == SYSTEM.layer`。一个业务模块会使用多个系统层，一项系统能力也会服务多个业务模块。

“两个视角”不同于系统内部“老师端 / 内部运营端”两个使用面，后者见 §5.5。

### 2.2 三条战略主线与四个业务域

Leon 已接受 `供给形成 / 价值实现 / 经营方式` 三条战略主线。v0.6 继续保留它们作为战略论证的组织框架，折叠展示在四域主图下方，并未撤回。

| 战略主线 | 论证用途 | 与四域图的主要联系 |
|---|---|---|
| 供给形成 | 怎样重复形成所需的高质量教师供给 | 供给制造、筛选、新师成长，以及贯穿过程的辨识与培养 |
| 价值实现 | 怎样把供给转化为持续的好教学 | 匹配、可靠授课、成长、回报与客户价值输出 |
| 经营方式 | 怎样让经营判断和行动成为持续运行的能力 | 日常运营、跨域 Hive、共同事实与规则、全局供需 |

此表是解释性映射，不是互斥归属表。“经营方式”不等于 SYSTEM 页，“价值实现”也不只等于业务图最右侧两个产品模块。

## 3. BUSINESS：业务全景

### 3.1 四个业务域与关键阶段

```text
B1 供给制造 ──候选老师──> B2 筛选 / TIDE
                                  │ 合格转正
                                  ▼
                         G 新师成长 → 熟练稳定

B3 日常运营：持续支持筛选、新师成长和成熟老师
B4 客户价值输出：匹配发生在授课前，也服务 TIDE 的实课试用

学生需求、实际教学与客户结果反向校准 B1 / B2 / G / B3 / B4
```

上图表达状态与服务关系，不是一次通过、单向移交的流水线。TIDE 期间已存在真实课堂、匹配和运营支持，日常运营也不以毕业为唯一开始条件。

| ID | 模块 | 业务语义与边界 | 当前依据 |
|---|---|---|---|
| B1 | 供给制造 | 选择供给来源和组织方式，形成候选教师及未来有效产能 | 已确认，S1 C-08/C-12/C-16 |
| B1-O | Online / 居家 | 老师各自居家教学，重点方向为教师转介绍 | 已确认方向；效果、占比和资源未定 |
| B1-C | Offline / Center | 老师集中于 Center 工作，包括自营与合营；重点是战略共识与模式建设 | 已确认方向；学生仍在线上课 |
| B2 | 筛选 / TIDE | 用真实试用课堂及反馈辨识合格老师，与招聘流程贯通；相同授课任务采用共同质量标准，供给模式可采用不同培养与取证方法 | 已确认讨论边界，S1 C-04/C-05/C-12 |
| G | 新师成长 | 从合格转正到熟练稳定，覆盖能力、曝光与适配订课、收入形成和履约操作支持 | 独立阶段已确认，S1 C-06；具体机制仍待设计 |
| B3 | 日常运营 | 五项功能持续互动，经营全部老师；以 Agent Hive 支撑大规模信息处理、协同和反馈 | 已确认，S1 C-12 |
| B4 | 客户价值输出 | 让合适老师被学生发现、选到、约到，并以真实教学形成持续客户价值 | 已确认方向，S1 C-12；具体实现待设计 |

Center 的语义必须保留：

- Online / Offline 区分的是教师工作组织方式，不是学生线上 / 线下学习渠道。
- Center 是一种供给模式，不只是招聘渠道、培训地点或便宜产能。
- Leon 报告的当前条件是：以现有培养能力和物理环境，只有 Center 模式能把这类教育专业毕业生快速培养成合格老师，当前居家模式不具备相应条件。这是该路径当前的硬前提，不应扩大为永久结论。
- 提高 Center 地位不等于批准扩张比例、取消居家模式、接受某项预算或确认各模式经济性。

**标准适用范围**：同一授课任务采用共同质量标准；不同供给模式可以采用不同培养与取证方法；不同课程与区域明确适用标准。跨语言、学科、级别和学生类型时，统一验证协议与证据要求，再引用适用的具体标准，不能把单一总分无条件通用。资格与试教准入见 §5.2。

### 3.2 B3 的五项日常功能

| ID | 功能 | 业务作用 | 必须连接的反馈 |
|---|---|---|---|
| B3-1 | 鹰眼 | 逐师、逐课、逐要素感知教学与履约 | 信号进入判断、画像、沟通及改进；保留未覆盖和不确定部分 |
| B3-2 | 沟通阵地：AC＋老师 APP | 与老师进行多内容、多形式、双向沟通并支持办理与行动 | 不止送达；要理解反馈、跟进行动，并核对问题是否解决 |
| B3-3 | 薪资与升降级 | Pay Good Teachers More 2027：让质量、能力、责任和回报形成更有效关系 | 依据真实证据和有效规则，观察激励效果与误伤；本文件不设定生效政策 |
| B3-4 | 培训与持续成长 | 按短板和目标提供支持，持续改变能力 | 用后续课堂变化验证学习效果，不能以完成课程或任务数替代 |
| B3-5 | 全员老师画像 | “老师的一生.md”：全程共享老师的事实引用、状态、证据和判断 | 新事实、执行及复检修正后续判断；一次评分不能自动变成永久标签 |

五项功能不是五个人工项目加一个 AI 工具。目标运行方式是：Agent 持续处理信息、形成任务、调用能力、追踪结果；人制定目标与规则，处理关键例外并承担最终责任。

`.md` 是全员老师画像的表达隐喻，不是已决定用 Markdown 文件充当生产数据库，也不是已确定存储架构。

### 3.3 B4 的两个明确模块

- **师生匹配**：由匹配规则、推荐引擎和“轻松选到好老师”的产品共同组成。匹配与授课时段、资格、能力和学生适配有关；TIDE 实课试用也需要匹配与订课。
- **老师包装外化**：“好老师在 51Talk”，把真实能力和教学证据转化为用户可理解的表达。不能用包装替代实际质量，曝光、点击或成交也不能独立证明教学价值。

### 3.4 三项全局基础能力

| ID | 能力 | 业务语义 | 与首期建设的关系 |
|---|---|---|---|
| F1 | 数据治理与本体 | 统一事实、状态、对象关系及语义，让模块能够引用同一事实基础 | 两个首批场景需要其中的具体部分；不表示全域治理已完成 |
| F2 | Law & Standards | 好老师 / 坏课定义、工作流、每一步行动规则，以及基于反馈修订规则 | 参与判断、行动约束和贯穿治理，不能只等同一份质量量表 |
| F3 | 全局供需计算 | 把学员需求、存量老师、开课、有效产能和新招老师纳入统一模型 | 必须属于 Tutor OS；其算法建设范围不自动包含在 2＋2 之内 |

F1/F2/F3 是业务全局能力分组；它们与 SYSTEM 的 CAP-1/CAP-2 不处于同一分类维度。

### 3.5 两条贯穿线与跨域运行

**辨识与培养是各自作用、互相影响的两条线。** 辨识回答当前能力、适配和短板；培养改变能力；真实课堂提供新的辨识证据。两条线贯穿试用、新师成长与成熟教师经营，不能分别锁在转正前后。

**Hive 跨域运行关系：** 感知变化 → 依据共同事实与规则形成任务 → 跨模块行动 → 核对真实结果 → 反馈改进。业务系统实际完成开课、排课等动作。图中的箭头是运行机制设计，不是接口已经打通的证明。

## 5. SYSTEM：共同主干与语义契约

本节是技术化解释及设计建议，不是可直接执行的数据库或 API 规范。

### 5.1 共用主干：四段职责与贯穿治理

| 职责 | 责任 | 典型内容 / 产出 | 关键约束 |
|---|---|---|---|
| 事实与证据 | 接入具有来源与时效的业务事实及观察 | 官方签收事实引用、待验证课堂信号、回复、身份引用、时段与执行证据 | 两类输入显式区分；保留缺失、迟到、质量、不确定和覆盖缺口 |
| 业务对象与状态 | 将事实引用组织为可持续经营的对象与关系 | 课程交付及恢复案例、授课资格，以及老师档案、证据、任务和复检记录 | 状态可独立查询与推进；不再造原课堂、排课或身份事实正本 |
| 判断与规则 | 按适用规则、证据与情境形成判断或行动意图 | 资格、适配、风险、归因、训练建议、供需判断 | 保留适用范围、证据与规则版本；未知不直接判为合格或有责 |
| 行动与结果 | 通过能力接口和对应执行主体完成真实动作 | 沟通、训练、排课、恢复、复检及结果回写 | 调用成功与业务完成分开；失败、超时、无响应须有后续 |
| 贯穿治理：权限、审计与评测 | 行动前约束权限，过程中追踪，结果可复核纠错 | 授权证据、Trace、Eval、申诉、纠错、版本与责任 | 贯穿四段，不是执行后的最后一站 |

```text
权限、责任与适用规则 ───────────────────────────────────────────
                       ↓              ↓               ↓
事实与证据 → 业务对象与状态 → 判断与规则 → 行动与结果
                   ↑                              │
                   └── 真实结果 + 新证据 + 复检结论 ─┘
审计、评测、申诉纠错与版本管理 ─────────────────────────────────
```

本稿停止使用自定义 L0—L4 编号。此前本稿及系统参考用“L3 执行”，与公司已有“L3 数据资产”命名发生冲突。本地规则锚点见 S13；CEO Agent 所引 Shared“L3 官方事实、L3.5 业务语义”为 S10 的来源报告，**本轮未直接核验 Shared 原文，也不建立这四段与 Shared 层级的一一映射**。

“已签收的官方事实”与“待验证的观测信号”统一引用各自原事实源，携带标识、时间、版本和质量信息。签收不等于事实永远正确，正式记录仍可能被更正。未核实信号可以按既有授权触发保护或恢复，但不能自动成为正式归责；事实更正应影响关联状态与下一次判断。

CAP-1/CAP-2 是横向能力：鹰眼持续为事实与复检供给证据；全触达同时参与观察反馈、执行支持和结果确认。Hive 为任务组织、能力调用与结果回流提供共享运行支持。

### 5.2 共用对象：兑现状态、资格状态及支撑记录

先问两个问题：**学生这一节课现在兑现到哪一步？老师现在被允许在什么条件下教什么？** 原有四类对象是支撑起点，不能以处理过程替代这两个结果。

| 业务对象或关联 | 最低语义内容 | 主写 / 引用边界 |
|---|---|---|
| 课程交付 `LessonDelivery` 与异常恢复案例 `RecoveryCase` | 关联原排课、课堂和承诺；当前交付状态、受损情况、恢复安排与尝试、实际结果、关闭证据、接收与后续追踪责任 | 优先引用现有排课／交付对象；正常课也有兑现结果。恢复案例关联原课，不与课程交付混成一套状态；原事实和客户服务动作由对应系统维护 |
| 授课资格 `TeachingQualification` | 教师身份、语言／学科／课程级别／学生类型／区域及交付条件，验证证据、规则版本、有效期和复检状态 | 资格须结构化、可查询；引用实际资格主写方。试教准入与正式资格区分，不能从档案总分自动推出全部课程资格 |
| `LessonEvidence` 课堂证据 | 关联课程、时间、来源、观察、证据引用与质量状态 | 原始课堂事实留在事实源；Tutor 引用并形成领域判断 |
| `TutorProfile` 老师档案 | 身份关联、资格记录引用、能力证据、可靠性状态、当前任务与结论版本 | 汇聚关系与状态视图，不成为第二套课堂、排课或资格事实库 |
| `OutreachTask` 触达任务 | 目标、关联课程／案例／老师、渠道、送达、回复、理解结果、行动与超时升级 | 复用任务和渠道能力；触达任务完成不等于课程兑现或资格复检完成 |
| `RecheckRecord` 复检记录 | 原问题、整改动作、方法与窗口、新证据、结论及对课程／资格的影响 | 领域负责复检语义；执行沿用共享任务协议，结果回到所关联对象 |

上述英文名称都是冷读概念标识，不声称生产中存在同名表、接口或类。对象数量不构成数据库表数量；已有对象能承载就建立引用。字段类型、唯一标识、版本、实际主写方及状态枚举仍需工程契约定义。

**课程兑现的状态约束：**

- 已承诺、实际交付、证据待核、受损、恢复中、结果核实等，是需要区分的状态含义，尚不是冻结的枚举或转换表。
- 同一课程可关联多次恢复尝试；一次尝试失败仍须能继续追踪原问题。
- 老师整改完成、通知已发、替代方案已提出、工单已转交，都不能自动关闭课程问题。关闭须有真实交付／客户处理结果及适用关闭依据；无法恢复时保留原因、后续处理和责任。
- 转交必须取得接收确认；接收前由谁继续追踪、超时向谁升级、接收后谁负责关闭，须在场景契约中定义。不能写一句“Service 负责”就认为交接完成。

**资格与 TIDE 的状态约束：**

- 实课用于取证，因此须先定义受约束的试教准入：允许教什么、对应哪些学生、需要何种支持、何时停止。试教许可不等于正式授课资格，待验证也不等于无条件允许试教。
- 正式资格在对应范围内成立的必要条件：`适用范围明确 ∧ 样本充分 ∧ 交付底线通过 ∧ 教学质量达标`。未知项保留待验证；总分只在满足适用条件时使用，不能抵消交付底线失败。
- 资格有效性、到期、限制、暂停、恢复及复检应可查询；具体触发条件及执行权限回有效规则。资格与“当前具备授课条件”、责任归因分别判断。
- 出营后的新课堂及客户结果用于检验筛选与培养是否有效；独立性来自新样本、结果来源和复核机制，不要求另造一套相反的质量标准。

对象中必须区分 `事实引用 / AI 判断 / 人工决定 / 执行结果`。观测到网络异常可以进入事件与条件证据，不能未经归因写成老师过错。

**统一档案是统一身份关联、状态语义和引用关系，不是把所有数据装进一份 Markdown。** 课程兑现与资格需要独立状态，证据、任务和复检通过关联支持它们。

### 5.3 Tutor 领域、Hive 与实际执行主体

| 责任 | Tutor 领域应定义 | 共享平台 / 对应系统应承载 |
|---|---|---|
| 任务 | 两场景状态转换、优先级、超时升级、业务完成条件 | 通用任务生命周期、调度、执行与恢复机制 |
| 对象 | 业务语义、判断、资格、结果关联 | 身份、事实源访问及共享数据能力；主写边界按对象确定 |
| 权限 | 动作风险、允许范围、人工确认点 | 身份鉴权、权限执行与授权记录 |
| 执行 | 何时沟通、训练、匹配、恢复、复检 | 渠道、业务系统动作及技术 / Service / Center 的实际处置 |
| 证据与 Eval | 业务案例、标注标准、结果与误伤判据 | 通用 Trace、回放、评测运行及版本能力 |

该表表达建议的责任划分，不是 Hive 已经交付全部能力的声明。实际可调用接口、版本、权限、限制、样例、缺口和交付证据仍需回源验证。缺口的最小实现也应遵守共享契约，避免形成一套长期平行的“小蜂巢”。

“在 Tutor OS 框架内”与“由 Tutor 团队亲手执行”是两种关系。平台故障可由技术负责人修复，客户恢复可由 Service 承接，场地问题可由 Center 处理，系统仍需追踪同一业务事件的结果。

### 5.4 归因与人的责任

对异常至少分开三个判断：

1. `customer_impact`：这节课是否受损，学生需要什么恢复？
2. `delivery_readiness`：现在是否具备继续授课条件？
3. `accountability`：原因是否可归责老师，应由谁承担责任？

设备位于老师侧，不自动证明老师有责；不归责老师，也不自动证明授课条件恢复。归因不明应保持待核实状态，客户恢复继续推进。涉及惩罚、停课、重大课量或课酬合同变化等敏感动作，须依有效权限与人工责任机制处理，不能由本文件授予自动执行权。

参考中的全记录边界包括：教学相关内容范围、非相关隐私排除、老师可见可纠错可申诉、只汇聚事实引用与判断。统一档案方向有确认输入；具体数据用途、权限及公司层面的规则仍需确认，不能将参考页里的建议直接当作正式个人数据或人事政策。

### 5.5 同一系统的两个使用面

- **Teaching / 老师端**：理解学生、备课、复盘、训练，了解自己的状态、短板、任务和课量，解释与纠错。
- **Operations / 内部运营端**：供需规划、风险识别、分层、匹配、异常处理、改善验证。

这是产品与使用者划分，不是 BUSINESS / SYSTEM 双图划分。只有内部监控后台而没有老师得到支持的路径，无法完整表达目标系统。

## 7. 两个场景如何检验共同系统

本节为示例运行链，用于理解建设逻辑，不是已经上线的 SOP。

### 7.1 BF-1：一次履约异常

1. 鹰眼观测到异常，保留原课程、时间、来源、信号及覆盖信息；未确认部分保持不确定。
2. 将证据关联原课程交付对象、老师和恢复案例；分别判断客户影响、当前授课条件与责任归因，不直接写“坏老师”。
3. 依据适用规则和权限形成行动意图。需要替代老师时，查询相应时段可用供给与资格范围，执行前再次核验；查询有结果不等于已预约或已完成替代。
4. 通过沟通、业务系统及对应团队推动召回、替代交付、技术处置等动作。无人可用、资格不明、无响应、失败或超时进入明确后续。
5. 转交须取得接收确认并持续追踪原课；多个恢复尝试关联同一交付问题，触达或整改任务关闭不自动关闭课程。
6. 以实际课堂／客户处理结果核对兑现状态；无法恢复时保留原因及后续处理依据。设备技术复测、课的恢复与责任裁定分别留证。
7. 按适用方法复检，把新证据与结果写回课程、案例、资格及档案引用，影响下一次匹配、支持或观察重点；规则变化按权限与版本机制处理。

两场景的联系：该场景暴露的原因与可改进短板，可校准 TIDE 的训练、试教准入、资格证据和复检重点；客户恢复不等待所有归因完成。

### 7.2 BF-2：一位新老师的真实试用

1. 从居家或 Center 路径进入的候选老师关联同一身份；按适用条件取得受约束试教准入。来源或所属模式不能直接替代资格证明。
2. 通过最小供给查询、试教范围检查、匹配与订课获得真实试用课堂；没有适配课位时记录缺口并进入安排或升级，不能把没有课堂当作没有问题。
3. 鹰眼与客户反馈形成课堂证据，按适用标准分别评价交付底线、教学质量及成长；样本不足保持待验证。
4. 识别短板后，使用共享触达和任务机制支持训练，用新课堂证据复检；发生坏课时调用 BF-1，继续追踪学生的实际交付。
5. 在样本充分、交付底线通过、质量达标等条件内作出相应范围的资格结论，记录规则版本、有效性及复检要求。总分不能跨过未通过的底线。
6. 出营后把资格与证据接入匹配和新师成长；继续核对稳定授课、适配订课、收入形成与日常操作支持。
7. 用出营后的新课堂和客户结果检验此前筛选与培养是否有效，避免用同一批评分自证正确；必要时复检资格并改进训练与支持。

30 天描述单个老师的试用周期。新师成长从合格转正后开始；90 天项目验证窗口来自架构师建议，不是已批准建设期限。

### 7.3 共用是否成立

两个场景同时出现同名功能，不足以证明复用。应能追踪：同一教师身份、同一事实引用方式、可关联的课程兑现、资格、任务与复检记录、共同规则版本、可回放动作，以及某场景结果是否实际影响另一场景或后续经营。

“共用一套主干”不要求两场景使用完全相同的业务状态机、阈值或流程；共用的是基础协议与能力，领域语义仍按场景定义。

## 8. 全局供需统一算法：保留完整地位

已确认的业务问题是：存量老师、学员数量、开课量和新招老师数量需要统一计算，目前被 Leon 描述为“割裂的几个数字自己自洽”。这是业务缺口输入，不是本轮对所有现存模型作出的全量审计结论。

冷读时应理解为如下计算契约，**不是已冻结的公式**：

```text
同一时间窗及分层下的需求
        对照
存量老师有效可交付产能 + 预计按时进入的合格新增产能
        ↓
识别数量 / 时段 / 资格 / 适配等缺口
        ↓
比较存量开课与激活、成长、调配、招聘等补足动作
        ↓
实际预约、履约、完课与客户结果回流，校准下一轮预测
```

最少要明确：

- 时间窗、区域、课程 / 能力与时段粒度；各口径具有一致单位和范围。
- 老师人数、开放可约课位、实际预约、实际完课和有效教学是不同量，不能相互替代。
- 新增招聘存在筛选、训练、转正与产能形成的时间差；新招人数不能直接等于当期有效产能。
- 同一老师、同一时段的课位，即便适配多个能力类别，也不能在汇总产能时重复占用。
- 同时检查存量调节与新招需求，不能把每个缺口都直接换算成招聘人数。
- 参数、事实和版本可追溯，预测与实际可对照；阈值和生产算法仍需专门定义。

业务图把 F3 放在全局基础能力位置；运行上可由 Hive 持续调度并向各业务域形成任务。**能力归属、计算口径、运行主体和图上位置是四个不同问题。** 把它移到某个页面区域，不会自动解决统一算法。


### 8.1 完整算法与首期最小依赖

完整算法负责需求预测、存量有效产能、合格新增产能及招聘／成长／调配的统一计算；它可以不在首期完成。**首期两个场景仍必须拿得到适配试用课位和可用替代老师，因此最低运行依赖不能空置。**

| 最小依赖 | 必须回答 | 承接与失败语义 |
|---|---|---|
| 供给查询 | 对指定课程、学生类型、区域、时间窗，哪些老师和课位当前可用？ | 指明原数据源、更新时效与查询能力；区分未找到、数据未知、服务失败及确实无供给 |
| 资格检查 | 候选老师是否具备本次试教／正式授课所需范围与有效条件？ | 引用有效资格和规则版本；未知不自动放行，转相应核验／安排 |
| 真实安排 | 查询后能否实际预约、锁定或完成替代？ | 执行前重查资格与可用性，由已有排课／交付主体完成并回传结果；防止同一课位重复占用 |
| 缺口承接 | 无适配课位、无替代老师、无响应或资格不明时，谁持续追踪，何时升级？ | 进入有接收确认和后续结果的安排／恢复路径；不能用“人工兜底”四字替代运行契约 |

首期承接说明应列出来源、时效、接口／工具、实际执行主体、范围限制、失败出口和验证样例。复用现有系统优先；所需最小实现遵守共享契约，不另建长期平行系统。这是 BF-1/BF-2 的运行前提，不新增第三个战场，也不声称现有能力已经可用。

## 11. 给接续 AI 的使用方法与冷读自检

### 11.1 接续工作方法

1. 先说明当前分析主语是 BUSINESS、SYSTEM，还是两者的联系；避免不加区分地说“这个模块应该移到底座”。
