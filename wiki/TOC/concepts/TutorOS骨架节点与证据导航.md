# Tutor OS 骨架节点与证据导航

云端返回总图：[【A】Tutor OS](https://alidocs.dingtalk.com/i/nodes/vNG4YZ7JnPDjwzGdsARRx9OnW2LD0oRE?utm_scene=team_space) · [Teacher battle · Leon wiki](https://alidocs.dingtalk.com/i/nodes/GZLxjv9VGqKl0mPvHZooPyla86EDybno?utm_scene=team_space)

返回[[TutorOS知识总图]]。本页由 Agent 维护，展开已认领骨架并连接证据；新增解释与页面归类属于导航工作，不逐页请求 Leon 签字，也不把导航推论升级为正式业务结论。引用页的历史、设计、已审与候审状态分别保留。

## S0

**Tutor OS：全球真人教学供给与持续交付经营系统。** 同时经营逐课交付与长期教师能力、产能、关系和收益；提供相互连接的目标、经营对象、责任、事实、行动与反馈。

Learning 提供学习需要与跨课掌握；Tutor 组织真人供给和教师交付；Service 承接体验与权益；Growth 连接需求与商业价值。共同课堂事实支撑协同，不由 Tutor 独占全部责任。

- 依据：[[TutorOS设计宪法全文]] §1–4、§7、§12；版本与原件从[[TutorOS建设]]回读。
- 导航：[[TOC成立后-教师运营系统地图与责任清单]]、[[TutorOS首期运行契约与2＋2验收缺口]]。
- 检验：一项工作能否说明客户结果、协同责任、动作和结果证据？总体设计不能证明各能力已经运行。

## M1

**Home-based Teacher：经营当前主流的居家教师供给。** 准入与招募 → 训练和成长 → 可用时段与师生适配 → 真实交付与远程支持 → 收入、留存与后续成长，是一条完整经营链。

平台直接联系、设备网络保障、AI 与远程训练、适当的导师支持都应接到真实课堂。导师与伙伴网络是可探索的组织支持方式，不能在导航时将具体职位、收入或机制写成现行规则。

- 存量定位：[[2026-09-14-TutorOS知识骨架认领与共建分工#模式纠正原话]]；设计依据：宪法 §8、§10–11。
- 现有入口：[[招聘战役]]、[[好老师生命周期]]、[[新师训战营]]、[[薪酬改革]]、[[外教触达原子小队]]。这些是相关经营知识，是否适用具体 HBT 群体仍回正文与实际规则。
- 渠道区分：[[Referral重启]]属于招聘渠道；它不能代表 HBT 全部经营，也不能排除对 Center 教师的适用可能。
- 反例检查：给居家教师增加培训或沟通次数，若没有改善后续课堂、实际收入或支持体验，不能证明主流供给已被改善。

## M2

**Center-based Teacher：与 HBT 同层的中心供给模式。** 它已有供给基础，当前需要加强 owner、教学负责人、训练、文化、现场管理、设备环境及可复制经营。

两条模式都有招募、成长、适配、交付、收入、留存问题。Center 额外需要解释共同现场条件和经营者价值；架构上并列，不要求二者当前规模或近期投入相同。

- 依据：本轮[[2026-09-14-TutorOS知识骨架认领与共建分工]]、宪法 §8–11。
- 现有入口：[[Center模式]]；业务问题与证据从该页继续展开，历史试验与当前治理要求分开。
- 反例检查：低缺席或高利用率不自动证明学习效果；公共网络或管理问题不应全部归因给个体老师。

## F1

**Every Lesson Counts：每课兑现客户价值、留下理解老师与学生的证据，并成为后续课改善的起点。** HBT 与 Center 共用这一交付、观察、反馈和改进原则。

共同回路是：两种模式各自的组织与支持 → 真实课堂 → 证据、反馈和行动 → 改善教师与经营方法 → 后续课堂验证。证据分别积累到学生学习、教师条件化能力、可验证的方法；长期目标可以跨课验证，未兑现的课堂承诺也要被看见。

- 依据：宪法 §3–6、§16；9 月 9 日正式纪要的 Lesson 基础单位确认，见[[2026-09-09战略会正式产出与TutorOS建设规划]]。
- 现有入口：[[好老师生命周期]]、[[TutorOS首期运行契约与2＋2验收缺口]]。
- 反例检查：一节巩固课没有即时分数上涨，仍可能帮助长期保持与迁移；该例仅解释边界，需要后续证据验证，不是实测案例。

## N1

第二层：[[TutorOS经营域-D01-学习需要与交付承诺|D01 学习需要与交付承诺]]

**学习需要与承诺。** 从学生任务、课程、市场与时段的需要出发，组织能兑现的教师供给，区分需求、预约与真实承诺。

- HBT：所需能力与时段是否有真实可用的分散供给？Center：现场出勤和固定安排怎样接到同一需求？
- 入口：[[外教侧需求X-Y-Z需求地图]]、[[X-Y-Z三轴经营模型]]、[[2026-07-31-CC预约体验课动态标签供给]]；宪法 §2–3、§10。
- 容易误读：需求预测、预约数量不能替代合格教师在具体时段的实际可用性。

## N2

第二层：[[TutorOS经营域-D02-教师获取与准入|D02 教师获取与准入]] · [[TutorOS经营域-D03-新师成材与早期经营|D03 新师成材与早期经营]] · [[TutorOS经营域-D04-产能与供需配置|D04 产能与供需配置]] · [[TutorOS经营域-D05-授课条件与模式治理|D05 授课条件与模式治理]]

**形成并经营供给。** 从线索、准入、launch、可预约机会到稳定合格的好课供给，辨清每一段的对象、条件和损耗。

- HBT：招来、带出、上好、留下的完整链条。Center：在同样链条上连接招募、席位、到岗、支持与经营。
- 入口：[[招聘战役]]、[[Referral重启]]、[[新师训战营]]、[[新老师上岗后供给流水线与预测口径-待验证问题卡]]、[[Center模式]]；宪法 §7–9。
- 容易误读：launch、席位或教师人数增长，不自动等于增加可用的高质量课位。相关数字冲突仍见[[外教转介绍数据口径冲突与待核清单]]。

## N3

第二层：[[TutorOS经营域-D06-教师价值呈现与匹配|D06 教师价值呈现与匹配]] · [[TutorOS经营域-D07-师生关系与跨师承接|D07 师生关系与跨师承接]]

**师生适配与关系。** 让资格、能力、学生任务、时段和支持条件形成合适配对，并接住后续关系与跨课信息。

- HBT 与 Center 都需处理固定时段、持续关系、临时代课与质量；Center 的稳定现场条件也需要实际证据支持。
- 入口：[[直通车项目]]、[[2026-05-26-师生匹配双供应商竞赛与统一入口]]、[[2026-08-18-精选老师推荐六项准入定稿]]；宪法 §2、§6、§10、§17。
- 容易误读：固定同一老师不保证教学连续性；换师也应有跨课承接。推荐信号不自动成为资格、排序或薪酬规则。

## N4

第二层：[[TutorOS经营域-D08-好课判断与逐课证据|D08 好课判断与逐课证据]] · [[TutorOS经营域-D09-履约恢复与问题治理|D09 履约恢复与问题治理]]

**每课的真实交付。** 分别观察可靠履约、有效学习、持续认可与异常恢复；记录实际条件和证据缺口。

- HBT：远程课堂、网络设备、履约与求助。Center：个体课堂与公共环境、管理和现场支持的共同作用。
- 入口：[[坏课KPI设计稿]]、[[抓共性负向项]]、[[外教触达原子小队]]、[[2026-08-26-坏课治理双方案灰度拍板]]；宪法 §3–6、§17。
- 容易误读：看见、触达、整改和客户结果分别核验；坏课 KPI 设计不因挂在这里就生效。

## N5

第二层：[[TutorOS经营域-D10-教师成长与教学支持|D10 教师成长与教学支持]] · [[TutorOS经营域-D11-教师体验与公平治理|D11 教师体验与公平治理]]

**教师成长与支持。** 从真实短板或发展机会出发，给到可用帮助，观察教师是否实际应用，并由后续课堂验证效果。

- HBT 的远程训练、AI 与导师帮助；Center 的 Head Teacher、带教和现场支持，都是这一问题的不同实施条件。
- 入口：[[好老师生命周期]]、[[老师质量提升飞轮]]、[[新师训战营]]、[[成熟老师升降级积分方案]]、[[2026-09-04-老师成长两箱与积分方案分叉]]；宪法 §6、§8–9、§16。
- 容易误读：支持下的好表现和教师能迁移的能力分别判断；培训量、反馈次数或分数变化不能单独证明成长。

## N6

第二层：[[TutorOS经营域-D12-教师所得与激励|D12 教师所得与激励]] · [[TutorOS经营域-D13-全成本与可持续经营|D13 全成本与可持续经营]]

**收入与供给可持续。** 一起看教师实际净收入、单位总投入时间回报、稳定性、留存及平台全成本；Center 还涉及经营者价值。

- 两种模式分别保留课量、等待、备课、培训、设备与支持条件，识别增收来自何处、能否持续。
- 入口：[[薪酬改革]]、[[入门期薪酬倾斜]]、[[成熟老师升降级积分方案]]、[[老师也是客户但要用结果验证]]；宪法 §11、§19–20。
- 容易误读：多上课、临时补贴或转嫁成本，不自动证明单位回报提高；不能重复扣除已进入净收入的成本。

## N7

第二层：[[TutorOS经营域-D14-事实标准与协同执行|D14 事实标准与协同执行]] · [[TutorOS经营域-D15-方法沉淀与系统进化|D15 方法沉淀与系统进化]]

**有效方法与系统能力。** 从真实案例提出方法假设，验证适用条件，观察实际采用与效果，再复用、修订或退役。

- HBT 与 Center 都能产生方法；从远程搬到现场或反向迁移时，重新核对人群、任务、环境和支持条件。
- 入口：[[TutorOS首期运行契约与2＋2验收缺口]]、[[TOC成立后-教师运营系统地图与责任清单]]、[[人工流程产品化AI化]]；宪法 §12、§16。
- 容易误读：写出一页方法、生成一个工具、部署一次系统和产生持续业务效果是不同层次。

## 关系怎样接受检验

| 关系 | 当前理解 | 要找的证据 |
|---|---|---|
| N1 → N2 / N3 | 需求指导供给与匹配 | 同一市场、课程、时段的需求和可兑现产能 |
| N2 → N3 → N4 | 合格可用供给形成承诺并交付 | 准入、可预约、适配与课堂实际结果的对应 |
| N4 → N5 → 后续 N4 | 课堂证据触发支持，支持改善后续课堂 | 实际应用、后续结果及条件变化 |
| N4 ↔ N3 | 本课更新关系与承接，历史帮助下节课 | 信息实际被承接，学生任务是否延续 |
| N4 → N6 → N2 / N5 | 交付价值经合理分享支持可持续供给 | 增量价值、实际收益、投入及全成本；因果需验证 |
| N4 / N5 → N7 → 其他节点 | 验证后的方法改善新的经营场景 | 独立验证、实际采用、适用边界与失败案例 |
